# mypage2026

ポートフォリオサイト。何を載せるかは `docs/site.md`、見せ方は `docs/design.md`。

## 粒子モーフの仕組み

写真の全画素を粒子として描き、N枚の写真の間を任意の順序で遷移させる。

対応付けはペアごとに作らない。各画像を独立に**輝度ランク空間**へ写す。

```
写真a ─sort─┐
写真b ─sort─┼→ ランク k = 0..粒子数-1（全画像共通の粒子ID）
写真z ─sort─┘
```

粒子 k は「どの写真でも k 番目に暗い画素」という一つの意味を持つので、任意の
2枚が自動的に接続される。対応表は画像ごとに1つ（計 N 個）で済み、a→e→z→a と
巡っても誤差が蓄積せず厳密に元へ戻る。モノクロ＝輝度が1次元で全順序が付くこと
が前提で、これは1次元の最適輸送そのもの。

### データの持ち方

hero 専用の画像は持たず、Photos で広げたときの拡大用の画像（`large-1200`、1200×800）を読む
（`src/photos/manifest.ts` の `heroSrc`）。中央を 3:2 で切り出し、粒子グリッドの解像度に縮めてから輝度を取る。
ソート結果は元画像から一意に決まるので持っても情報が増えず、座標列は圧縮も効かない。
輝度を8bitに量子化したカウントソートは 88 万粒子で実測 5〜6ms
（`src/hero/table.ts`）なので、実行時に作るほうが速くて軽い。

カウントソートが安定ソートであることも効いている。画素を走査順にバケットへ流し
込むので、同輝度の画素は「上から下・左から右」に並ぶ。空や壁のような平坦部が塊
のまま移動するのはこの副作用。

粒子グリッドは読む画像の解像度（1200×800）が上限で、VRAM 予算（120MB）とテクスチャ上限に収まる
ところまで落とす（31 枚でも 1200×800 のまま、約 114MB）。画面サイズは見ない。
写真の枠は CSS で幅 1110px（`MAX_PHOTO_WIDTH`）までにして、大きい画面で粒子が引き伸ばされて粗くならないようにする。

GPU には RGBA8 のデータテクスチャ `t_table` を1枚だけ置く。N枚ぶんの表を縦横に
敷き詰めたアトラスで、1テクセルが粒子1つ。

| チャンネル | 内容                                                                      |
| ---------- | ------------------------------------------------------------------------- |
| RGB        | ランク k → 元画像の画素インデックス（24bit LE）。シェーダで格子座標に戻す |
| A          | その粒子の輝度                                                            |

座標ではなくインデックスを持つのは、3バイトに収まって A が空くため。作品がモノクロ
なので、色は輝度1バイトで足りる。アトラスの列数は「確保するブロック数が最小で、同数なら
正方形に近い」ものを選ぶ（横一列では 16384px の上限に 21 枚で当たる）。

頂点シェーダは `u_from` / `u_to` の2ブロックを `texelFetch` して `mix` する。
1粒子が読むのは2テクセルなので、**描画コストは写真の枚数に依存しない**。

### 粒子ごとの時間差

粒子ごとに、**暗さ**で出発時刻をずらす。暗い粒子ほど遅れて出発する。

```glsl
darkness = 1.0 - (lumFrom + lumTo) * 0.5   // 両端の平均。逆再生でも同じ順序になる
delay    = pow(darkness, u_toneCurve) * u_staggerTotal
local    = easeInOut((u_phase - delay) / (1 - u_staggerTotal), u_easePower)
```

光が先に抜け、闇が後から追う。`easeInOut` は指数つきで、`u_easePower` が 1 なら
等速、3 なら easeInOutCubic と一致する。既定値は `src/hero/tuning.ts`。

#### 速さとカスケードのトレードオフ

`staggerTotal` を大きくすると出発のばらつきは広がるが、残りの `1 - staggerTotal` が
1粒子あたりの移動時間なので、**同時に個々の粒子は速くなる**。両立はしない。

#### 調整のしかた

パラメータは uniform なので実行時に変えられる。`npm run dev` で開いた画面の左上に
スライダーのパネルが出る（`import.meta.env.DEV` の中でのみ描画され、本番バンドルには
入らない）。値は localStorage に残るのでリロードしても消えない。**既定値を変えても
保存された値が勝つ**ので、既定の挙動を確かめるときは「既定値」を押すか localStorage を消す。

値が決まったら「コードをコピー」を押して、`src/hero/tuning.ts` の `DEFAULT_TUNING` /
`DEFAULT_INTERACTION` に貼り替える。パラメータの定義（範囲・ラベル・説明）も
`src/hero/tuning.ts` にあり、worker の既定値とパネルの両方がそこを唯一の出典として使う。

`staggerTotal` を 0 にすると、ずらしなしで全粒子が同時に動く。

### 起動

全枚数を待たずに描き始める。worker は 0 番の写真だけ単独で先に上げ、届いた時点で
静止画として描く。残りは順番をばらして 8 並列で上げ、1枚上がるごとにメインスレッドへ
番号を返す。抽選はその時点で上がっている写真の中からだけ行い、
次の1枚が未定のあいだは時計を止めて静止帯の頭で待つ（遷移の途中で行き先が決まると
粒子が飛ぶため）。カレンダーの未読み込みの番号は薄く出し、押せない。

トップの HTML には hero のチャンクと一覧の先読み、worker のスクリプトと最初の写真の
prefetch が入る（`scripts/prerender.js`、`worker/index.ts`）。JS の起動と並行して
後ろの段を取り始めるため。Photos も同じく、一覧の先読みと最初の数枚の preload が入る。
HTML に埋め込む写真の一覧は、R2 ではなく Cloudflare のキャッシュ（データセンターごとに 60 秒）から読む。
公開するとそのデータセンターの分を消す。

## 自動再生

hero は 100svh の1画面で、スクロールは写真の切り替えを操作しない。時計で自分で進み、次の1枚は
**ランダムに選ぶ**。全部を表示し終えるまでは、その巡で表示した写真を選ばない（一巡するまで重複しない）。
カレンダーでは、その巡で表示した番号をまだの番号より明るく出す。表示した数は、丸がその番号へ移った時点で数える。

進行状態は `src/hero/sequence.ts` が持つ。ランダム順なので「進捗から (from, to) を
逆算する」形にはできず、`{from, to, elapsed, history}` を状態として保持して時間で進める。
1周は静止帯 → 遷移帯。

`(from, to, phase)` の算出は**メインスレッドが持つ**。DOM のインジケータが同じ値を
必要とするため。worker は渡された3値を描くだけの純粋なレンダラで、時計を持たない。
phase は**線形**で、イージングは頂点シェーダが粒子ごとに掛ける（粒子ごとに開始時刻を
ずらすため、CPU 側でイージング済みの値を渡すと各粒子の加減速が制御できなくなる）。

「今の1枚」の答えは2つある。丸が示すのは遷移の開始で切り替わる側、粒子が位置として
近いのは中点で切り替わる側。同じ番号を押しても何も起きない判定は前者、番号を押した
ときの出発点は後者を使う。行き先が変わった瞬間は基準位置が跳ぶので、その差を
「ズレ」（下記）に振り替えて見た目の位置を保ち、バネが新しい軌道へ引き戻す。

自動再生を切っても進行中の遷移は完走させてから止まる（散ったまま凍結すると事故に
見えるため）。画面外では `IntersectionObserver` で時計を止める。
`prefers-reduced-motion` のときは初期 OFF で、動かすときも中点で切り替えるだけにする。

state に載せるのは現在の index と読み込み済みの番号だけ。`phase` のような
連続値を state に入れると毎フレーム再レンダリングが走るので、ref 経由で直接 style を書く。

## 干渉（マウス・指）

粒子は写真上の位置に加えて「ズレ」を持つ。ズレは粒子1つにつき1テクセルの
RGBA16F テクスチャ（ズレ xy と速度 zw）に入っていて、毎フレーム別のテクスチャへ書き
ながら交互に入れ替える。更新をフラグメントではなく頂点側で計算しているのは、
フラグメントの sampler が lowp 既定で、半精度の状態を読むと精度が落ちるため。

ポインタの速度に比例した「目標のズレ」が、距離でガウス減衰しながら掛かる
（放射状の押しと進行方向の引きずりの合成。向きは粒子ごとに乱数でずらす）。粒子は
目標へバネで引かれ、力が消えれば目標は 0 なので**必ず元の写真に戻る**。バネは
剛性ではなく「戻る秒数」と「減衰比」で指定する。暗い粒子ほど重く、質量は暗さの
指数関数なので比で効く。質量で加速度ごと割るため、固有振動数も減衰比も粒子ごとに散る。

ポインタ速度は瞬間値ではなく時定数で均す（上がるときは遅く、下がるときは速く）。
`stopBelow` を 0 より大きくすると、均した速度がそれを下回ってから戻りの猶予が過ぎた
時点で更新を止められる。既定は 0 で、粒子が見えているあいだは止めずに回し続ける。

## トップの舞台

トップは hero と光の層（`src/light/`）を 1 枚の canvas に重ねて描き、画面に貼りつけ（sticky）、その上をロゴと導線の段
（ふつうのページの中身）がスクロールで流れる。canvas と worker は `src/scene/` の 1 つで、hero と光はそれぞれ自分の層に描き、
worker が 1 回の全画面の描画で重ねる。各場面の区間は `src/app/stage.ts` にまとめてある。
写真はスクロールしても動かない。カレンダーだけがふつうのページの中身として上へ流れていきながら薄れ、スクロールしていることを示す。
少し（画面の 2 割）スクロールすると、粒子はスクロール量によらず時間で光の位置（画面の中央）へ加速して飛び込み、着いた粒子から
光に吸い込まれて消える。光はスクロールに合わせてゆっくり（1 画面ぶんかけて）上がり、画面の上寄り（高さの 2 割）で止まる。
写真を出発した粒子は、写真の層から光の層へ移り、自分の明るさの光の粒として光線と同じ層に描かれる（粒子がそのまま光になる）。
光は着いた粒子の分だけ明るくなる（戻ると時間で逆にたどり、粒子は光から出て写真へ戻る）。
集まり始めたあとも速くスクロールしたときは、スクロール量に合わせて集まりを先へ進める。光はそこから、ページの一番下までスクロールするあいだに、全周に広がる光から下向きの光に絞られていく（光のパネルの
「光の広がり」）。
光はついた直後は暗く（最大の 5 割）、スクロールでロゴが近づくにつれて明るくなり、ロゴが画面に入る前に最大になる。ロゴと導線はページの中身と同じくスクロールで
下から上がってきて、光の下に入る。最後はロゴが画面の中央の高さ（横は少し左）に収まる。段は光の層にとっての部屋で、段の中央から少し左にロゴを描き、段の位置は毎フレーム要素から取る。壁や床は置かず、ロゴに当たらなかった光はそのまま抜ける。
床の上にはロゴを下から照らす光（スポット）を置き、部屋が画面の下端に近づくと光り始める。ロゴの切り込みのうち 2 本は下に開いていて、
上の光だけでは奥まで光が入らず、mu と読めないため。
訪問者はロゴと光を変えられる（`light/arrangement.ts`）。ロゴはドラッグで動かし、ピンチ（指 2 本、トラックパッド）で大きさを変えられる。
光がついているあいだ、フッターの左にロゴの設定とライトの設定を出す（`light/LogoControls.tsx`）。どちらもアイコンを押すと上に開く。
ロゴの設定は素材（白い面・和紙（光が中へ入って散り、内側から光る）・つや（鏡の向きの近くに返す））と大きさ。
ライトの設定は上の光と下の光それぞれの向きと明るさで、向きはふだん Auto（ロゴの今の位置を向き、動かすとついてくる）。
光源の位置は変わらない。変えたロゴと光の置き方は、フッターの戻す操作で既定へ戻せる。

光の層は 2D の光の経路追跡で、光線の通った線を重ねて描く。仕組みは `src/light/scene.ts` の冒頭。
光線の数は端末の速さに合わせて変える（`light/rayBudget.ts`）。worker が光の 1 フレームを描き終えたら知らせ、メインスレッドは
知らせが来るまで次のフレームを送らない。知らせの間隔から 0.3 秒ごとにフレームレートを測り、60fps 近く出ていれば上限まで増やし、
出ていなければ下限まで減らす。開発中は、今のフレームレートと本数を開発用ドックに出す。

| `index.html`                | ページの雛形。初めて開いたとき（タブごとに 1 回）のスプラッシュを HTML と CSS だけで持つ。JS を待たずに動き、ロゴが組み上がってナビのロゴへ移る                                                                                                                                                                                                            |
| `scripts/fonts.js`          | 本文の書体（Zen Kaku Gothic New）を、プリレンダした全ページに出てくる文字と英数字だけに絞って woff2 にし、各ページの先頭で先読みさせる。元のフォントは `fonts/`（OFL）。開発中は絞らずに `src/dev-fonts.css` で読む                                                                                                                                        |

Worker には `requestAnimationFrame` がないため、駆動はメインスレッドの rAF から。
タブが非表示になると rAF が止まり、無駄な描画も止まる。

## 制約

- 全写真のアスペクト比を揃える必要がある（粒子集合を共有するため）。現在は 3:2。
- 対応の根拠は輝度の順位だけなので、意味的な対応（顔と顔）は起きない。
- 粒子グリッドは起動時に決まり、以後は変わらない。画面サイズは見ず、VRAM予算と
  テクスチャ上限に収まらないときだけ配信解像度から落とす。
- モノクロ専用。色を輝度1バイトに畳んでいるため、カラー写真は扱えない。
- `glaku` は 0.5.2 以上が必須。頂点シェーダの sampler を highp で注入し、
  `createTexture` が `Uint8Array` を受けるのがこの版から（`docs/glaku.md`）。

## 写真の管理

写真の正本は R2（バケット `mypage2026-photos`）。サイトは起動時に `/api/manifest` から
一覧を読み、画像は `/images/<kind>/<name>` から取る。再ビルドなしで写真を入れ替えられる。

| キー                       | 内容                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `manifest.json`            | 一覧。`file / w / h / category / hero / tag / caption / v` の配列。形は `src/photos/manifest.ts` が検証する。`category` は Photos の street / abstract / color と、Works に並ぶ works。`hero` はトップの hero での順番（1 から。使わない写真は持たない）、`tag` と `caption` は Works の案件の種類と説明の 1 行（案件の最初の写真だけが持つ）、`v` は派生画像の版（下記） |
| `list-<長辺>/<file>.webp`  | 一覧用。長辺 200 / 400 / 800 / 1200px、画質 60                                                                                                                                                                                                                                                                                                                            |
| `large-<長辺>/<file>.webp` | 拡大用。長辺 1200 / 2000px、画質 80、カラー、トリミングなし。一覧で広げたときと、トップの hero（1200、`hero: true` のもの）が読む                                                                                                                                                                                                                                         |
| `originals/<file>.<ext>`   | 原本。再派生のために置く。認証なしでは取れない                                                                                                                                                                                                                                                                                                                            |

API は `worker/index.ts`。読み取りは誰でも、書き込みと原本の取得は Cloudflare Access の
JWT を検証する（`worker/access.ts`）。`ACCESS_TEAM_DOMAIN` と `ACCESS_AUD` が未設定なら
localhost からの書き込みだけ通す（wrangler dev 用）。

問い合わせフォーム（`src/app/pages/ContactForm.tsx`）は `POST /api/contact` へ送り、Worker が Turnstile の
答えを確かめてから本人の Gmail へメールで送る（`worker/contact.ts`、送信は `send_email` の binding）。
`TURNSTILE_SECRET` が未設定なら localhost からだけ確かめずに通す。wrangler dev ではメールを送らず、
中身を一時ファイルに書き出す。

派生の段（長辺と画質）は `src/photos/manifest.ts` の `VARIANTS` が唯一の定義で、表示・Worker・管理画面・
スクリプトがここを読む。写真ごとに、一覧は「表示幅 × 画面の密度 × 1.5」、拡大は「表示幅 × 画面の密度」以上で
一番小さい段を選ぶ（`src/photos/index.ts` の `pickSource`）。一覧の 1.5 倍は余裕で、等倍で出すと画質 60 の
圧縮の荒れが見え、マウスを載せたときのズームで引き伸ばされるため（`LIST_HEADROOM`）。スマホの 6 列なら 400、
PC の密度 1 倍の 3 列なら 800 と、表示に見合う段だけを読んで転送量とデコード後のメモリを減らす。一覧で一覧用の
最大でも足りないとき（PC の高精細な画面の縦長）は拡大用の 2000 を使う。Photos の HTML は、先頭数枚を `imagesrcset` で先読みさせる（`worker/index.ts`）。

画像の URL には版の印 `?v=<v>` を付ける。`v` はその写真の派生を全部つないだ中身のハッシュで、書き出し直して
中身が変わったときだけ変わる（`scripts/encode-photos.mjs` と `src/editor/derive.ts` が同じ決め方で付ける）。
印付きの URL は中身が変わらないので、Worker は 1 年持ってよい（`immutable`）と返す。

**Service Worker（`src/sw/`）。** 本番だけで登録する。ローディングを感じさせないためのもの。

- 印付きの画像と、名前にハッシュが付く JS・CSS・フォントは、手元にあれば手元から出す。HTML と一覧は通信で
  最新を取り、取れないときだけ手元のものを出す。2 回目以降の訪問は、ほぼ通信を待たずに表示される。
- 表示に要る読み込みが落ち着いたら、その端末で列数をどれにしても一覧に要る段を、今のカテゴリから順に
  全カテゴリぶん先読みする（`src/gallery/prefetch.ts`）。一覧用の段だけで、拡大用（高精細な画面の 2 列などで
  一覧にも使う）は先読みしない。データセーバーがオンのときと、回線がごく遅い
  （slow-2g）と見積もられたときは先読みしない。今の一覧に無い版（差し替えや削除で古くなったもの）は消す。
- 最初の訪問ではページを途中から引き受けない（読み込みの途中に割り込むと遅れるため）。次の訪問から通す。
- ビルドごとに `sw.js` が変わり、新しい Service Worker がすぐ入れ替わって、前のビルドの JS・CSS を消す。
- 止めたいときは、`register()` の代わりに既存の登録を `unregister()` するビルドを出す（`sw.js` を消すだけでは
  入っている Service Worker は残る）。`http://<LAN の IP>` は安全な接続とみなされないので、`dev:lan` や
  `preview:lan` では動かない（localhost では動く）。

**サイトの上での編集（`src/editor/`）。** `/admin`（Access で保護）でログインすると、このブラウザに目印を残して
元のページへ戻る（`src/app/pages/Login.tsx`）。目印のある人だけ `/api/session` でログイン中かを確かめ、通れば
編集用のコードを動的 import で読み込む（`src/app/editing.ts`）。訪問者は問い合わせも読み込みもしない。
右下の操作バーで「編集」を切り替える。編集中の Photos では、写真に hero・カテゴリ・差し替え・削除の操作が
重なり（マウスは載せたとき、指は触ったとき）、一覧の先頭の「＋」かファイルを落として写真を足す（カテゴリの先頭に入る）。
差し替えは新しい名前の写真として同じ位置に置き、元の写真を消す予定にする。
並べ替えは写真をつかんで動かす（マウスは押して動かす、指は長押しで持ち上げる。`src/editor/drag.ts`）。下に来た写真の
位置へ移り、ほかの写真は Gallery が場所を空ける。画面の上下の端に近づけると自動でスクロールする。
編集中のトップでは、操作バーの「hero を編集」で下からパネルが開く（`src/editor/HeroPanel.tsx`）。上段が hero の並び
（番号順。つかんで横に並べ替え、× で外す）、下段が全写真（触ると hero の末尾に足す・外す）。閉じたときにまとめて
下書きへ入れ、hero はそこで作り直す（hero に渡す並びが変わると作り直す。`src/app/pages/Top.tsx`）。
変更は下書き（このブラウザの localStorage）にためて「公開」で
manifest.json を丸ごと置き換える。追加した画像は選んだ時点で R2 に置き（破棄したら消す）、削除した写真の
画像は公開のときに消す。派生画像はブラウザで作る（`src/editor/derive.ts`。段階的な縮小、WebP 書き出し。
Safari は WebP を書き出せないので Chrome を使う）。

**最初の移行と作り直し**（段を変えたときなど）は次の順。`.photos/` は作業用で追跡しない。

```
npm run photos:originals   # 本番の一覧を .photos/manifest.json に取り、手元に無い原本を本番の R2 から .photos/originals/ へ
npm run photos:encode      # .photos/originals/ → .photos/<kind>/。一覧の順番・カテゴリ・hero は引き継ぐ
npm run photos:import      # .photos/ → ローカルの R2。npm run dev で確かめる
npm run photos:push        # → 本番
```

原本は管理画面で足したものだけが本番の R2 にある。それ以前の写真の原本は手元にしかないので、
`.photos/originals/` に置いておく（`photos:originals` は手元にあるものは取りに行かない）。

**写真の移動**は `scripts/sync-photos.mjs`。一覧（manifest.json）を正として、
各段と hero を etag で比べ、違うものだけ送る。送り先の一覧にだけある写真は
画像ごと消す。原本は送らない。`npm run dev` を動かしたまま使う（ローカル側は
wrangler dev の API 経由）。本番への書き込みは wrangler なので、ログインしておく。

```
npm run photos:import      # .photos/ → ローカル
npm run photos:pull        # 本番 → ローカル。管理画面で本番に足した写真を手元に揃える
npm run photos:push        # ローカル → 本番。実行前に何が変わるか出して確認を求める
node scripts/sync-photos.mjs push --dry-run   # 変更内容だけ見る
```

push は本番の一覧を丸ごと置き換え、ローカルにない写真を本番から消す。本番で足した写真を
消さないよう、push の前に pull するか、dry-run で差分を見る。

## 開発

```
npm install
npm run dev       # Vite（:5173）。写真の API（wrangler dev、:8787）も一緒に立ち上がり、
                  # /api と /images はそちらへプロキシされる。ローカルの R2 を使う
npm run dev:api   # Worker だけを単体で動かすとき
npm run dev:lan   # dev を LAN にも出す。手元のスマホから http://<Mac の IP>:5173 で見る
npm run preview:lan  # 本番ビルドを LAN に出す（:8788）。実機で滑らかさを見るときはこちら
npm run bench     # 読み込みと操作中の滑らかさを測る（bench/README.md）
```

LAN に出すのは自宅など信頼できるネットワークだけにする。開発サーバはソースをそのまま配り、
VPN など Mac のほかのネットワークにも出る。スマホからは管理画面の書き込みは通らない
（Worker が宛先の host で localhost からの書き込みだけ通すため）。スマホのページは、iPhone なら
Mac の Safari の Web インスペクタ、Android なら Chrome の chrome://inspect から計測できる。
`http://<IP>` は安全な接続とみなされないので、Service Worker などはこの方法では試せない。

Worker の型 `worker-configuration.d.ts` は `npx wrangler types` の生成物で、リポジトリに置く。
`wrangler.jsonc`（バインディングや `compatibility_date`）を変えたら作り直してコミットする。
build では生成しない。生成は workerd を起動し、Cloudflare のビルド環境ではそこで止まってデプロイが進まなかったため。

ローカルの R2 は空なので、最初に写真を入れる。本番にあるなら `npm run photos:pull`、
原本からなら上の作り直しの順。

一覧は画面の上下 2.5 画面ぶんの写真だけを描き、描いた時点で画像を読み始める。読み込みが
終わってから現れ、離れたら要素ごと外してデコード済みの画像を手放す（メモリの少ない端末での
カクつき対策。写真が増えても描く要素の数は変わらない。`src/gallery/Gallery.tsx`、`src/gallery/Img.tsx`、
`src/gallery/reveal.ts`）。段組は `src/gallery/layout.ts` が計算する。各写真を順に、いちばん上が
空いている列へ置く。広げる写真は幅を px で自由に取れ、覆う列の下に置き、覆わなかった列には
後ろの写真が入るので、幅をどこで止めても自然に詰まる。上にあった写真は動かさない。
クリックした写真はその場で全幅（縦長は画面の高さに収まる幅）に広がり、周りは押し下げられる。
もう一度押すか Esc で戻る。広げられるのは 1 枚で、別の写真を押すと前の写真を戻しながら広げる。
広げた写真も画面から離れたら大きい画像を手放す。
動きは FLIP で、変更前と変更後の位置を配置の計算から出し、差分を transform で戻す（DOM から位置を読まない。`src/gallery/Gallery.tsx`）。

**Node 20.19+ / 22.12+ が必要**（`package.json` の `engines`）。Vite 8 と TypeScript 7 が
それより古い Node では起動しない。nvm を使っているなら `nvm use 24` など。

## 本番の準備（Cloudflare 側）

1. R2 を有効にし、バケット `mypage2026-photos` を作る。
2. 原本を `.photos/originals/` に置き、`npm run photos:encode` → `npm run photos:import` → `npm run photos:push`
   で写真と manifest を入れる。原本は入れない。
3. Zero Trust > Access で Self-hosted のアプリケーションを作り、パス `/admin` だけを保護する。
   自分のメールだけ許可する。Access はメソッドを区別できないので `/api/*` や `/images/*` は
   入れない（入れると一覧の画像が誰にも見えなくなる）。書き込み API は Worker が
   Access の Cookie（`CF_Authorization`）の JWT を検証して守る。編集の fetch は同一
   オリジンなので Cookie が自動で付く。
4. `ACCESS_TEAM_DOMAIN`（`<team>.cloudflareaccess.com`）と `ACCESS_AUD`（アプリケーションの
   Audience タグ）を Worker の secret に入れる（`wrangler secret put`）。dashboard の
   plain-text 変数は `wrangler deploy` で消えるので secret にする。
   未設定のままだと本番の書き込みはすべて 503 になる。
5. Email Routing を mu826.com で有効にし、`hello@mu826.com` を Gmail へ転送するルールを作る。
   Gmail は転送先として確認済みにしておく（問い合わせフォームもこのアドレスにしか送れない）。
6. Turnstile のウィジェットを作り（住所は mu826.com と workers.dev）、Site Key を
   `src/app/pages/ContactForm.tsx` に、Secret Key を Worker の secret `TURNSTILE_SECRET` に入れる。
7. `npm run deploy`。
